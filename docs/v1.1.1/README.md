# v1.1.1：诊断信息补全，兼容会转发数据包的网络驱动

## 1. 为什么做

2026-10-24 起，一位玩家（小米笔记本 + 手机热点，Windows 11）反馈：加速开着，Nexon 登录器一直转圈；重启电脑、关开加速几次后有时又能用。用他的诊断包排查时，缺几项关键信息，只能靠猜：

- 登录器到底有没有发起连接，连的是 IPv4 还是 IPv6；
- 交给节点的是域名还是 IP，节点有没有回应；
- 电脑当时的网络环境：网卡、IPv6、DNS、系统代理；
- 开始加速时界面上的提醒（游戏已在运行、冲突），日志里没有。

于是先补诊断信息，再借助几个测试版找到原因：他的电脑上有个驱动会转发已建立连接的数据包，分流核心看不到这些包（经过见第 5 节）。这一版包括两部分：诊断信息，以及对这类驱动的兼容（修复）。加速规则不变。

## 2. 改了什么

### 修复：兼容会转发数据包的网络驱动

- 有些电脑上的驱动会把已建立连接的数据包截下来再重新发出：TCP 是握手之后的包，UDP 从第一个包开始。以前分流核心会跳过这类包，于是：
  - 登录器只有每条连接的第一个包走了节点，Nexon 登录器一直转圈；
  - HTTP/3（UDP）整条走了直连，像没开加速。
- 现在分流核心会把这类包接回来，照常按规则处理，玩家不需要卸载任何软件。
- 遇到这种电脑时，日志里会写一行“检测到本机有其他网络驱动转发数据包，已自动兼容”。
- 如果那个驱动连 MSBOOST 发出的包也会转回来，两边就会来回转发。MSBOOST 发现后会自动关闭兼容，写一行“数据包在 MSBOOST 和其他网络驱动之间来回转发，已关闭自动兼容；如果加速无效，请导出诊断包联系客服”。测试中没有出现过这种情况。
- 普通电脑上没有这类包，行为和以前一样。

### 连接记录（日志新增“连接”分类）

- **名单内程序的新目标**：加速期间，名单内程序（以及已开启的 Discord、Steam）每访问一个新目标，记一行：程序名、TCP 或 UDP、是否 IPv6、目标地址和端口、处理方式（加速、直连、拦截，或“改由 MSBOOST 接管（系统代理）”）。同一程序访问同一目标只记一次。
- **交给节点的连接**：每条连接结束时，记下交给节点的目标（域名，或者没拿到域名时的 IPv4/IPv6 地址）、上行和下行字节数、用时。上行有数据而下行是 0 的，标注“没有收到任何回应”。同一目标只记一次，没有回应的另记一次。网络检测自己的探测不记。
- **上限和统计**：每次加速两类各最多记 200 条。停止加速时写一行统计：访问的目标数（加速、直连、拦截，其中 IPv6 多少）；经节点的连接数（域名、IPv4 地址、IPv6 地址），其中多少条没有回应；超过上限没写出的条数。
- **只记名单内程序**：浏览器、聊天软件等其他程序的连接一律不记。
- 日志页新增“连接”筛选。

### 开始加速时写进日志

- **网络环境**：Windows 版本；系统代理（包括自动配置脚本）；每块正在使用的网卡的类型、IPv4/IPv6 地址、网关和 DNS。电脑自己的公网地址只显示前半段（IPv4 前三段，IPv6 前两组），能看出网络类型和运营商，但不暴露具体地址。
- **提醒**：开始加速前游戏已在运行、不阻止加速的冲突（例如 Netch 在运行）。以前只显示在界面上。

### 停止加速时写进日志（“分流”分类）

- **转交汇总**（`Hand-off summary`）：转给本地中转的连接和数据包数、中转转回的回应数、中转接收和关掉的连接数。用来判断加速连接有没有真正交到节点。
- **兼容汇总**（`Bridge summary`）：接回的被其他驱动转发的数据包数，按 TCP、UDP 分开，并分为加速连接的包和其他包。
- 中转因为检查没通过而关掉连接时，前 8 次各记一行地址。

### 诊断包

`system.txt` 增加：
- 网络环境（同上）；
- 游戏相关进程：名单内正在运行的进程，以及名字里有 nexon、maple 但不在名单里的进程。后者用来发现登录器更新后改了进程名。

## 3. 实现要点

- **连接决定**来自分流核心自带的连接回调。回调运行在唯一的收发包线程上，Go 这边只复制字符串放进队列，不做别的事。开启回调前打开分流核心的按目标去重，同一程序同一目标只回调一次。回调指针没有加锁，所以只在开始加速前设置、在分流核心完全停止后清除，加速途中不动它。
- **交给节点的连接**来自核心的本地 SOCKS5 入口：在原有的连接计数外再包一层，读出握手里的请求目标（账号密码直接跳过，不保存），之后只统计字节数。不改任何数据，也不拖慢转发。停止加速时最多等 2 秒，让还开着的连接写完记录再写统计。
- **网卡信息**用 GetAdaptersAddresses 读取，系统代理沿用 WinHTTP 接口。不读注册表，不启动外部命令，避免杀毒软件和 Chrome 误报。
- **兼容（补丁 P5，`third_party/patches/0003-impostor-bridge.patch`，新文件 `pb_bridge.c`）**：
  - WinDivert 把其他驱动注入的包标为 impostor，分流核心主句柄的过滤条件 `not impostor` 会跳过它们，以免两个驱动来回转发。
  - 补丁在主句柄下方（优先级 122）收取外发的 impostor TCP、UDP 包，再从主句柄上方（优先级 124，只发送的句柄）重新注入。WinDivert 只把自己注入的包交给更低优先级的句柄，而且不再标为 impostor，于是主句柄照常处理。
  - 防循环：同一个包如果带着更低的 TTL 又被收回来（WinDivert 重新注入 impostor 包时会把 TTL 减 1），就关闭兼容，其余的包原样放行。
  - 计数都是原子加一，日志条数有上限。
- 两行英文提示由 `internal/app/windows.go` 的对照表换成中文。测试会核对补丁里的原文，两边不一致时测试不通过。

## 4. 实测步骤

1. 开始加速，打开 Nexon 登录器并进入游戏，玩几分钟后停止加速。
2. 日志页切到“连接”：
   - 有 nexon_launcher.exe、MapleStory.exe 等的连接，处理方式是“加速”；
   - 有“经节点 …（域名）”的记录和字节数；
   - 停止后有“本次统计”。
3. 日志页切到“程序”：开始加速时有“网络环境”和“网卡 …”几行。
4. 导出诊断包：`system.txt` 里有网络环境和游戏相关进程。
5. 开着 v2rayN 的系统代理再加速一次：连接记录里有“改由 MSBOOST 接管（系统代理）”。
6. 加速中打开 Steam 可选加速：打开之后，steam.exe 的连接才开始被记录。
7. 对比 v1.1.0 和本版程序的字符串：没有新增注册表里的代理设置名、按名字结束进程这类容易被误报的写法。
8. 普通电脑：
   - 日志页切到“分流”，停止后有 `Hand-off summary` 和 `Bridge summary`；
   - `Bridge summary` 的计数都是 0，也没有“已自动兼容”的提示；
   - 加速和以前一样正常。
9. 那位玩家的电脑：
   - 退出 v2rayN 后只用 MSBOOST，登录器、游戏都正常；
   - 日志里有“检测到本机有其他网络驱动转发数据包，已自动兼容”。

## 5. 排查记录：转交失败（补丁 P5）

### 背景

那位玩家用 dev-917ff17（只有 Go 这边的诊断）导出的诊断包显示：
- 登录器的连接都判成了“加速”，核心也把它们转给了本地中转，没有发送失败；
- 但之后没有一条被中转接收，也没有一条到达节点；
- 经系统代理的连接（开着 v2rayN 的系统代理，由 MSBOOST 接管）都正常。

玩家另外反馈：官方 ProxyBridge 加 v2rayN 同样不行，只开 v2rayN 的 TUN 模式可以用。

本机连接（系统代理）是直接交给中转的。发往外网的连接要“掉头”：
- 核心把程序发出的连接请求改为发往中转端口，交换源地址和目标地址，当作收到的包注入；
- 中转的回应再用同样的办法转回程序。

TUN 模式和系统代理都不经过这一步，所以问题出在这台电脑上的掉头转交。

### 第一次测试（dev-6e490ee，核心里加了逐步诊断）

| 步骤 | 结果 |
|---|---|
| 登录器的连接请求转给中转 | 7 次 |
| 中转回应（旁听句柄看到的 SYN-ACK） | 14 次，每条连接 2 次，都不是其他驱动注入的 |
| 回应转回登录器 | 14 次。登录器没有重发请求，说明它收到了 |
| 中转接收的连接 | 0 |

握手的前两步都通了，但登录器发的第三个包（确认）中转一个也没收到。中转每条连接只重发一次回应就停了，说明登录器那边的连接很快被重置。

推断：登录器握手之后的包被别的驱动重新注入，带上了 impostor 标记，主句柄跳过了它们，于是这些包直接发到了真实服务器，服务器不认识这条连接，回了重置。WinDivert 2.2.2 驱动源码证实：凡是由别的驱动注入的包（`FWPS_PACKET_INJECTED_BY_OTHER`），都会标成 impostor。

玩家电脑上没有常见的第三方网络驱动。与网络有关、而开发机上没有运行的有三个：Defender 网络检查（WdNisDrv）、Win11 的 wtd、小米的 MiServiceDaemon。玩家卸载小米电脑管家后，v1.1.0 仍然不行，但中间多半没有重启，所以不能排除它。最终没有查出是哪个驱动；兼容方案不需要知道。

另外，“重发请求”计数实际上不会增加：核心遇到重发的 SYN 会先清掉旧记录，再按新连接处理。这次 7 个端口的 SYN 各出现一次，确实没有重发。

### 第二次测试（dev-8f750d1，桥只接回 TCP 加速连接的包）

| | 第一次（19:06） | 第二次（19:08–19:13） |
|---|---|---|
| 桥交回的加速连接包 | 1336 | 1077 |
| 桥放行的其他程序的包 | 1657 | 4226 |
| 中转接收的连接 | 35 | 57 |
| 结果 | 登录窗口能打开，输入账号密码时黑屏 | 登录成功，MapleStory 经节点连上了登录服务器（8484 端口） |

- 推断成立：那个驱动会重新注入所有程序已建立连接的 TCP 包。
- 两次都没有出现循环，说明那个驱动不会重新注入 WinDivert 注入的包。
- 还剩两处漏洞：
  - UDP 没处理：登录器的 HTTP/3（UDP 443）照样直连。HTTP/3 允许连接中途换线路，服务器就会看到玩家本地的 IP。第一次黑屏多半是这个原因。
  - 开始加速前就已存在的连接，桥判断它不是加速连接，也会放行。

### 第三次测试（dev-a634de4，桥接回所有包）

| | 19:35–19:39 | 19:41–19:45 |
|---|---|---|
| 桥接回的 TCP 包（加速连接 / 其他） | 2825 / 3473 | 166 / 695 |
| 桥接回的 UDP 包（加速连接 / 其他） | 427 / 21 | 0 / 0 |
| 开始加速前已存在、改走中转的连接 | 1 | 10 |
| 中转接收的连接 | 74 | 31 |
| 真实服务器发给加速连接的重置 | 0 | 0 |

- 日志显示，UDP 流的第一个包就已经被转发：第二版直接放行，整条 HTTP/3 连接都绕过了节点。
- 玩家反馈“很完美很流畅”。第一次会话里有 26 条连接“没有收到任何回应”，都是不到 1 秒、只发了一个包，是浏览器同时试 HTTP/3 和 TCP 时放弃的那一条，属于正常现象。

### 正式版的取舍

- **保留**：桥（接回所有外发的 impostor TCP、UDP 包）、防循环、两行英文提示（启动器换成中文）、停止时的两行汇总、中转关掉连接时的前 8 行记录。
- **删掉**：
  - 旁听句柄：只用于这次排查；
  - 逐个包的 `[DIAG]` 日志；
  - 测试版的 `pb_diag.c` 换成 `pb_bridge.c`，补丁改名为 `0003-impostor-bridge.patch`。

### 以后再处理

- DNS 记录里有时拿不到 IPv6 地址对应的域名，原因待查。
