# v1.1.1：诊断信息补全（加速逻辑不变）

## 1. 为什么做

2026-10-24 起，一位玩家（小米笔记本 + 手机热点，Windows 11）反馈：加速开着，Nexon 登录器一直转圈；重启电脑、关开加速几次后有时又能用。用他的诊断包排查时，缺几项关键信息，只能靠猜：

- 登录器到底有没有发起连接，连的是 IPv4 还是 IPv6；
- 交给节点的是域名还是 IP，节点有没有回应；
- 电脑当时的网络环境：网卡、IPv6、DNS、系统代理；
- 开始加速时界面上的提醒（游戏已在运行、冲突），日志里没有。

这一版只补诊断信息，加速规则和流程都不变。

## 2. 改了什么

### 连接记录（日志新增“连接”分类）

- **名单内程序的新目标**：加速期间，名单内程序（以及已开启的 Discord、Steam）每访问一个新目标，记一行：程序名、TCP 或 UDP、是否 IPv6、目标地址和端口、处理方式（加速、直连、拦截，或“改由 MSBOOST 接管（系统代理）”）。同一程序访问同一目标只记一次。
- **交给节点的连接**：每条连接结束时，记下交给节点的目标（域名，或者没拿到域名时的 IPv4/IPv6 地址）、上行和下行字节数、用时。上行有数据而下行是 0 的，标注“没有收到任何回应”。同一目标只记一次，没有回应的另记一次。网络检测自己的探测不记。
- **上限和统计**：每次加速两类各最多记 200 条。停止加速时写一行统计：访问的目标数（加速、直连、拦截，其中 IPv6 多少）；经节点的连接数（域名、IPv4 地址、IPv6 地址），其中多少条没有回应；超过上限没写出的条数。
- **只记名单内程序**：浏览器、聊天软件等其他程序的连接一律不记。
- 日志页新增“连接”筛选。

### 开始加速时写进日志

- **网络环境**：Windows 版本；系统代理（包括自动配置脚本）；每块正在使用的网卡的类型、IPv4/IPv6 地址、网关和 DNS。电脑自己的公网地址只显示前半段（IPv4 前三段，IPv6 前两组），能看出网络类型和运营商，但不暴露具体地址。
- **提醒**：开始加速前游戏已在运行、不阻止加速的冲突（例如 Netch 在运行）。以前只显示在界面上。

### 诊断包

`system.txt` 增加：
- 网络环境（同上）；
- 游戏相关进程：名单内正在运行的进程，以及名字里有 nexon、maple 但不在名单里的进程。后者用来发现登录器更新后改了进程名。

## 3. 实现要点

- **连接决定**来自分流核心自带的连接回调。回调运行在唯一的收发包线程上，Go 这边只复制字符串放进队列，不做别的事。开启回调前打开分流核心的按目标去重，同一程序同一目标只回调一次。回调指针没有加锁，所以只在开始加速前设置、在分流核心完全停止后清除，加速途中不动它。
- **交给节点的连接**来自核心的本地 SOCKS5 入口：在原有的连接计数外再包一层，读出握手里的请求目标（账号密码直接跳过，不保存），之后只统计字节数。不改任何数据，也不拖慢转发。停止加速时最多等 2 秒，让还开着的连接写完记录再写统计。
- **网卡信息**用 GetAdaptersAddresses 读取，系统代理沿用 WinHTTP 接口。不读注册表，不启动外部命令，避免杀毒软件和 Chrome 误报。
- 不改加速规则。分流核心只加了诊断补丁 P5（见第 5 节），只记录，不改变数据包的处理方式。

## 4. 实测步骤

1. 开始加速，打开 Nexon 登录器并进入游戏，玩几分钟后停止加速。
2. 日志页切到“连接”：
   - 有 nexon_launcher.exe、MapleStory.exe 等的连接，处理方式是“加速”；
   - 有“经节点 …（域名）”的记录和字节数；
   - 停止后有“本次统计”。
3. 日志页切到“程序”：开始加速时有“网络环境”和“网卡 …”几行。
4. 导出诊断包：`system.txt` 里有网络环境和游戏相关进程。
5. 开着 v2rayN 的系统代理再加速一次：连接记录里有“改由 MSBOOST 接管（系统代理）”。
6. 加速中打开 Steam 可选加速：打开之后，steam.exe 的连接才开始被记录。
7. 对比 v1.1.0 和本版程序的字符串：没有新增注册表里的代理设置名、按名字结束进程这类容易被误报的写法。

## 5. 测试版补充：转交诊断与桥接试修（补丁 P5）

### 背景

那位玩家用 dev-917ff17 导出的诊断包显示：
- 登录器的连接都判成了“加速”，核心也把它们转给了本地中转，没有发送失败；
- 但之后没有一条被中转接收，也没有一条到达节点；
- 经系统代理的连接（开着 v2rayN 的系统代理，由 MSBOOST 接管）都正常。

玩家另外反馈：官方 ProxyBridge 加 v2rayN 同样不行，只开 v2rayN 的 TUN 模式可以用。

本机连接（系统代理）是直接交给中转的。发往外网的连接要“掉头”：
- 核心把程序发出的连接请求改为发往中转端口，交换源地址和目标地址，当作收到的包注入；
- 中转的回应再用同样的办法转回程序。

TUN 模式和系统代理都不经过这一步，所以问题出在这台电脑上的掉头转交。具体断在哪一步，现有日志看不出来。

### 第一次测试（dev-6e490ee，只有诊断）

| 步骤 | 结果 |
|---|---|
| 登录器的连接请求转给中转 | 7 次 |
| 中转回应（旁听句柄看到的 SYN-ACK） | 14 次，每条连接 2 次，都不是其他驱动注入的 |
| 回应转回登录器 | 14 次。登录器没有重发请求，说明它收到了 |
| 中转接收的连接 | 0 |

握手的前两步都通了，但登录器发的第三个包（确认）中转一个也没收到。中转每条连接只重发一次回应就停了，说明登录器那边的连接很快被重置。

推断：登录器握手之后的包被别的驱动重新注入，带上了 impostor 标记。主句柄的过滤条件 `not impostor` 会跳过这类包，于是它们直接发到了真实服务器，服务器不认识这条连接，回了重置。WinDivert 2.2.2 驱动源码证实：凡是由别的驱动注入的包（`FWPS_PACKET_INJECTED_BY_OTHER`），都会标成 impostor。

玩家电脑上没有常见的第三方网络驱动。与网络有关、而开发机上没有运行的有三个：Defender 网络检查（WdNisDrv）、Win11 的 wtd、小米的 MiServiceDaemon。

另外，第一版的“重发请求”计数（`sent again`）实际上不会增加：核心遇到重发的 SYN 会先清掉旧记录，再按新连接处理，所以重发会以新的 `SYN from port …` 出现，端口重复。这次 7 个端口各出现一次，确实没有重发。第二版删掉了这个计数。

### 第二版：桥接试修

- **桥**：
  - 新开一个优先级低于主句柄的句柄，收取被其他驱动注入的外发 TCP 包。
  - 属于加速连接（或中转端口）的包，从一个优先级高于主句柄的发送句柄重新注入，主句柄就会照常转交。原理是 WinDivert 只把自己注入的包交给更低优先级的句柄，而且不再标为 impostor。
  - 其他包原样放行。
- **防循环**：放行的包如果又被那个驱动送回来（同一个包，TTL 少了 1），桥就自动关闭，退回原来的做法。
- **诊断补充**：
  - 登录器的后续包转给中转了多少（ACK、数据、FIN、RST）；
  - 真实服务器发给加速连接的重置；
  - 桥处理了多少包。
- **对其他电脑**：没有这种驱动的电脑上，桥收不到包，行为和原来一样。

### 第二次测试（dev-8f750d1，桥只处理 TCP 加速连接）

| | 第一次（19:06） | 第二次（19:08–19:13） |
|---|---|---|
| 桥交回的加速连接包 | 1336 | 1077 |
| 桥放行的其他程序的包 | 1657 | 4226 |
| 中转接收的连接 | 35 | 57 |
| 结果 | 登录窗口能打开，输入账号密码时黑屏 | 登录成功，MapleStory 经节点连上了登录服务器（8484 端口） |

- 推断成立：那个驱动会重新注入所有程序已建立连接的 TCP 包，桥把加速连接的包交回后，转交就正常了。
- 两次都没有出现循环，说明那个驱动不会重新注入 WinDivert 注入的包。
- 第一次黑屏的可能原因：登录器还有 UDP 443（QUIC，也就是 HTTP/3）连接，而桥只处理 TCP。如果 UDP 包同样被重新注入，QUIC 连接只有第一个包经过节点，之后的包直接发出。QUIC 允许连接中途换线路，服务器就会看到玩家本地的 IP。
- 另一处漏洞：开始加速前就已存在的连接，桥判断它不是加速连接，也会放行。

### 第三版：桥覆盖所有包

- 桥把被其他驱动注入的所有外发 TCP、UDP 包（IPv4 和 IPv6）都交回主句柄，由主句柄按规则处理，和正常电脑一样：
  - 加速连接照常转交；
  - UDP 也覆盖；
  - 开始加速前就已存在的连接，按规则处理。
- 防循环保护不变。
- 汇总按 TCP、UDP 分别统计"加速连接的包"和"其他包"。

### 其他发现（以后再处理）

- 没拿到域名的 IPv6 目标（Cloudflare 的 2606:4700::…）交给节点后都没有回应，可能是节点没有 IPv6。登录器之后会改用 IPv4，所以不影响使用，但每次会多等两三秒。
- DNS 记录里拿不到 IPv6 地址对应的域名，原因待查。

### 记录什么

核心日志（“分流”分类）里以 `[DIAG]` 开头的行，每类只写前 8 条：

| 日志 | 含义 |
|---|---|
| `SYN from port … turned to the relay` | 程序的连接请求已转给中转 |
| `app ACK/data/FIN/RST from port … turned to the relay` | 程序的后续包已转给中转 |
| `relay SYN-ACK … turned back to the app` | 中转的回应已转回程序 |
| `relay closed a connection …` | 中转收到了连接，但检查没通过，关掉了 |
| `watcher: relay SYN-ACK …` | 旁听句柄看到中转发出了回应 |
| `watcher: reset from … to proxied port …` | 真实服务器给加速连接发了重置，说明程序的包发到了真实服务器 |
| `bridge: … handed back` | 桥把一个被其他驱动注入的包交回主句柄（带 `proxied` 的是加速连接的包） |

停止加速时写三行汇总：`hand-off summary`、`watcher` 和 `bridge`。

旁听句柄只复制数据包，不拦截也不修改。桥只处理被其他驱动注入的包。计数都是原子加一，日志条数有上限。

### 怎么看汇总

| 汇总 | 说明 |
|---|---|
| bridge 行有交回主句柄的包，中转接收不为 0 | 推断正确，试修生效 |
| bridge 行为 0，watcher 有来自真实服务器的重置 | 程序的包发到了真实服务器，但不是经其他驱动注入的，要继续查 |
| 后续包转给中转的数量不为 0，中转接收为 0 | 包转给了中转，但中转没收到 |
| bridge 行写着已关闭（packet came back） | 那个驱动会反复注入，桥用不了，要换别的办法 |
| 中转关掉的连接不为 0 | 中转收到了，但检查没通过 |

找到原因后，再决定 P5 是保留（诊断功能或正式修复）还是删除。发布说明暂不写这一项。

### 测试步骤（发给玩家）

1. 关掉 v2rayN 的系统代理和 TUN，或者直接退出 v2rayN。
2. 打开测试版，开始加速，再打开 Nexon 登录器。如果能登录，就进游戏玩几分钟；如果转圈，等 1 分钟左右。
