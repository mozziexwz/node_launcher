## 用户看到什么

菜单 `[3]` 自动查询出口 IPv4、入口 TCP 延迟和全程连接延迟，三项结果独立显示。成功时维持简洁格式：

```text
当前出口 IPv4：192.0.2.10
当前到中转服务器延迟：160 ms
当前到游戏服务器延迟：170 ms
```

这些数字仅为界面示例，不能写死为修正量。失败显示具体原因，不显示 `0 ms`，不把入口值冒充游戏值。页面不增加指标说明段落、成功样本括号或配置菜单，回车返回原菜单。原有启动、停止和加载配置行为保持不变。

入口项测客户端直接连接当前配置中唯一入口 TCP 地址和端口的建连时间，独立尝试 3 次，每次最多 2 秒，取成功样本平均值。入口无法唯一确定、只有 UDP 端口、拒绝和超时分别显示原因。

游戏项采用下述全程协议。在已建立的代理会话中，客户端发出连接指令，远端节点实际连接游戏 TCP 端口，只有连接成功后才返回确认。客户端测量这一请求与确认的往返时间，取最多 3 次尝试中的成功样本平均值。入口测试失败不阻止游戏测试；只要当前本地 SOCKS5 可用，游戏项仍应尝试。

## 指标定义与适用边界

全程游戏耗时的计时范围是：

```text
客户端开始发送 connect 请求
    → 当前 MSBOOST 路径（可能包含中间透明转发）
    → 最终 MSBOOST 节点收到请求
    → 节点向游戏目标执行一次真实 TCP connect
    → 节点发送连接成功确认
    → 客户端收到完整确认行，停止计时
```

计时使用客户端单调时钟，不要求客户端与服务器对时。序列化请求在计时前完成；开始点在写入前；收到完整响应行立即停表，再做完整校验。只有校验通过的成功响应才能成为样本。

不在结果上叠加入口 TCP 值，不使用服务器提供的 elapsed/connect_ms，不等待游戏应用握手，也不将查询出口 IP 或建立测试会话的时间算入游戏值。

此值包含暖机后的代理链路往返、远端 TCP 建连和少量指令处理、调度及响应传输开销。不能承诺示例中的 `160 → 170 ms` 或 `30 → 120 ms` 精确成立，也不能把它等同于游戏内 Ping。真实数值取决于实际路径、目标连接速度及当时网络状态。

两类线路使用相同的客户端和节点协议：

| 线路示例（数值均为假设） | 入口项 | 游戏项的预期组成 |
| --- | --- | --- |
| 上海 → 西雅图 MSBOOST 节点 → 游戏；到节点约 160 ms，节点到游戏约 10 ms | 上海直接连接西雅图配置入口，约 160 ms | 经上海—西雅图会话请求节点连接游戏，约 170 ms 加少量处理开销 |
| 上海 → 日本透明转发 → 西雅图 MSBOOST 节点 → 游戏；上海到日本约 30 ms，日本到西雅图约 80 ms，节点到游戏约 10 ms | 上海直接连接日本配置入口，约 30 ms | 请求与回复穿过日本到西雅图，再包含节点连接游戏的等待，约 120 ms 加少量处理开销 |

**只在最终西雅图 MSBOOST 节点集成测速服务，日本透明转发服务器无需整改，也无需部署测速服务。** 日本转发须保持原有完整 MSBOOST 通道；如果它终止代理而不是透明转发，必须确认哪个节点实际负责连接游戏。表中算式用于解释路径组成，BAT 不读取这些分段数值，也不执行数值相加。

## 客户流程与节点定位

1. 项目组将 v2 服务集成到主项目原有新部署流程，客户照常部署自己的 VPS，不执行第二份安装命令。
2. 客户使用原有核心、配置与新 BAT。Windows 不需要 Python、tcping.exe、SSH 客户端或服务器密码。
3. 客户加载并启动自己的 MSBOOST 配置，然后按 `[3]`。
4. BAT 通过 `MSBOOST.exe describe config` 读取配置中的本地 SOCKS5 端口，通过该 SOCKS5 请求连接远端 **`127.0.0.1:20424`**。这个地址是代理路径终点节点上的回环服务，不是客户端直接连接 Windows 的 `127.0.0.1:20424`。读取失败时沿用启动器原有本地端口回退规则，不能宣称已经验证运行节点的身份。
5. 游戏目标只在 BAT 顶部修改 `GameAddress` 和 `GamePort`。节点按请求连接允许的公网 IPv4 目标，无需为每个游戏重新部署节点。

本地 SOCKS5 地址是 `127.0.0.1:<当前配置端口>`；SOCKS5 CONNECT 中的目标地址是 `127.0.0.1:20424`。实现必须区分这两个地址。

只支持当前无本地 SOCKS5 认证的使用方式。服务器选择用户名密码认证或其他认证方式时明确报错，不能发送空认证绕过。必须完整读取并校验 SOCKS5 握手及 IPv4、IPv6、域名形式的完整 CONNECT 回复；代理提前返回 SOCKS5 成功并不代表测速服务可用，仍必须等到有效 hello。

配置文件与已运行核心可能错位，例如仅修改了磁盘配置而未加载，或者本地 SOCKS5 端口被另一个进程占用。入口项依据读取的配置；游戏项遵循实际 SOCKS5 流量路径。v2 不携带客户端期望的公网 IP，`node_id` 只用于会话一致性，不能证明节点与磁盘配置属于同一身份。客户必须通过原加载流程使运行配置一致，项目组需在实测中覆盖这种错位情形。

多跳、入口/出口分离或透明转发场景中，服务必须位于最后执行目标 TCP connect 的 MSBOOST 节点。入口 TCP 项仍是客户到配置入口；游戏项应经过真实转发路径到最终节点。若核心禁止代理访问回环地址、把目标错误地解释为客户端回环、把请求分流到其他节点，或截断协议，就无法通过仅修改 BAT 修复，必须由项目组先验证和处理节点路径。

## v2 编码与校验合同

所有请求和回复均为 UTF-8、无 BOM、单行 JSON，以 LF 结束。可接收 CRLF；行尾 CR 属于行内容长度，解析时可作为 JSON 尾部空白处理。**LF 前最多 4096 字节**，因此 CRLF 中的 CR 计入 4096；只有 LF 不计入。读取必须支持任意分段，不得把一次 `Read` 当成一整条消息。

协议只允许扁平对象及下列规定字段。字段名大小写敏感，不允许重复字段、未知字段、数组、嵌套对象、null 或类型替代。不能使用“最后一个重复字段覆盖前一个”的宽松解析结果作为校验依据。

所有字符串的 JSON 原始内容只能使用不转义 ASCII 字符集 `[A-Za-z0-9_.-]*`；不接受 `\u0032`、反斜杠或其他转义。各字段还必须通过更具体的格式校验：

| 字段 | 合法值 |
| --- | --- |
| `version` | 整数 `2`，不接受字符串、布尔、浮点或指数形式 |
| `operation` | 精确字符串 `hello` 或 `connect` |
| `nonce` | 32 位小写十六进制字符串，每个请求重新生成 |
| `node_id` | 32 位小写十六进制字符串，服务进程启动时生成 |
| `target_address` | 规范 IPv4 字符串；四段十进制，各段 0–255，不含前导零 |
| `target_port` | 1–65535 的 JSON 整数，不接受字符串、布尔、浮点、指数或前导零 |
| `success` | JSON 布尔 `true` 或 `false` |
| `error` | 只允许下文规定的固定枚举 |

原始行不能混入 BOM、非法 UTF-8、多条 JSON 或尾随非空白内容。字符串外允许 JSON 空白 SP、HT、CR，LF 仅用于消息分帧；其他控制字符及字符串内控制字符一律拒绝。实际允许字段应按“请求类型及成功/失败”分别建立精确集合，而不是单一宽松大集合。

### hello

请求仅有 `version`、`operation`、`nonce` 三个字段：

```json
{"version":2,"operation":"hello","nonce":"0123456789abcdef0123456789abcdef"}
```

成功回复仅有原请求全部字段、`node_id` 和 `success:true`：

```json
{"version":2,"operation":"hello","nonce":"0123456789abcdef0123456789abcdef","node_id":"89abcdef0123456789abcdef01234567","success":true}
```

hello 不触发目标 TCP 连接，也不产生游戏延迟样本。一个会话先完成 hello，再处理 connect。hello 的字段、版本、nonce 或回复结构不匹配，都属于握手失败；不继续将该连接作为 v2 会话。

### connect

请求仅有 `version`、`operation`、`nonce`、`target_address`、`target_port` 五个字段：

```json
{"version":2,"operation":"connect","nonce":"abcdef0123456789abcdef0123456789","target_address":"35.155.204.207","target_port":8585}
```

成功回复必须原样回显这些字段，加上当前会话的 `node_id` 与 `success:true`，不得带 `error`：

```json
{"version":2,"operation":"connect","nonce":"abcdef0123456789abcdef0123456789","target_address":"35.155.204.207","target_port":8585,"node_id":"89abcdef0123456789abcdef01234567","success":true}
```

只有实际 TCP connect 成功后才能发送成功回复。目标连接成功后立即关闭，不读取或等待游戏握手内容。

语法和字段合法的请求若连接失败，回复原请求全部字段、`node_id`、`success:false`，另加一个 `error`：

```json
{"version":2,"operation":"connect","nonce":"fedcba9876543210fedcba9876543210","target_address":"35.155.204.207","target_port":8585,"node_id":"89abcdef0123456789abcdef01234567","success":false,"error":"timeout"}
```

`error` 精确映射如下：

| 枚举 | 含义 |
| --- | --- |
| `timeout` | 节点连接目标超时 |
| `refused` | 目标连接被拒绝 |
| `unreachable` | 网络或目标不可达 |
| `target_not_allowed` | 目标不是允许的公网单播 IPv4 |
| `failed` | 其他连接失败 |

协议非法、重复字段、超长行或无效会话顺序应关闭连接，不执行目标连接。合法请求产生的目标拒绝等失败可使用上述有效失败回复，客户端可继续复用同一会话。

v2 回复禁止加入 `connect_ms`、`samples`、`relay_address` 或其他统计字段。所有时长均由客户端测量。

## 暖机、尝试与重连时序

暖机有一个共享的 **5 秒总 deadline**，从创建本地 socket 开始，包含连接本地 SOCKS5、完整 SOCKS5 协商/CONNECT 回复、发送 hello 以及完整 hello 回复。不能把每个读取步骤的 5 秒重新起算。暖机耗时不进入任何游戏样本。

在同一条 TCP 会话上依序执行最多 3 次 connect，不并发、不流水发送。每次流程：

1. 生成新的 nonce，构造并序列化完整 connect 请求。
2. 启动客户端单调计时器，紧接着写入请求。
3. 在本次 **2 秒总 deadline** 内完成写入和完整回复行读取；每一步使用剩余时间。
4. 收到完整行时立即停止计时，然后验证精确字段、nonce、目标、版本、操作、`node_id` 与成功/失败结构。
5. 只有有效 `success:true` 才记录刚才的客户端耗时；有效 `success:false` 记录具体失败原因。

协议错误、EOF、本地读取或写入超时会污染会话边界，必须关闭并丢弃该连接。这一次算失败尝试；若尚有剩余尝试，再用新的 5 秒暖机建立新会话，重连暖机也不计入样本。有效失败回复允许在原会话继续下一次尝试。

任何重连 hello 失败，应立即结束剩余尝试，不反复无界重试。此前已成功的样本可以保留并参与平均。三次全失败时没有平均值；不得以零补齐失败样本。

服务端限制如下：

| 限制 | 值 |
| --- | --- |
| 单会话 connect 请求上限 | 3 次，失败请求也占一次 |
| 单会话空闲等待上限 | 3 秒 |
| 单会话总寿命 | 15 秒 |
| 单次目标 TCP connect 上限 | 2 秒 |
| 单次回复写入上限 | 2 秒 |
| 同时处理的会话上限 | 4 个 |

服务端读取分段、连接和写入都必须同时受会话剩余寿命约束，不得通过连续小片段或慢速读取无限续期。客户端 2 秒是端到端 deadline，包含转发时间，因此在较长路径上可能先于服务端目标连接超时；这是一次真实失败，不得超时后仍接收迟到成功。

## 迟到、重放与节点一致性

每次请求使用新 nonce，回复必须精确匹配当前 nonce、operation、version、目标地址和端口。之前一次请求的迟到回复或重复回复不能计作下一次成功。

hello 返回的 `node_id` 在同一会话内必须保持一致；connect 回复换了 `node_id` 就关闭会话并报错。服务进程重启时生成新 `node_id`，重新建立连接并通过新 hello 后可以接受变化，不应把旧 ID 永久绑定到某个公网 IP。

同一连接必须维护明确的行边界，一次请求只对应一条回复。客户端若在一次读取中发现 LF 后还有字节（包括第二行或其片段），立即按协议错误关闭会话，不静默丢弃后继续复用。若额外内容稍后到达，仍须通过下一次新 nonce 的校验，旧回复不能成为成功样本。协议异常后整条连接废弃，避免旧数据混入后续尝试。

nonce 与 node_id 用于请求关联和会话一致性，不是密码学身份认证。连接的鉴权和保护依赖现有 MSBOOST 通道及服务器本地访问边界，不应宣称它们能够抵御已控制节点的伪造。

## 节点安全边界

服务只绑定 **`127.0.0.1:20424`**，允许来源仅为 `127.0.0.1`；不绑定 `0.0.0.0` 或公网地址，不增加公网监听端口，不修改防火墙开放规则。节点通过已有 MSBOOST 的认证路径转接到本机服务。

服务仅接受公网单播 IPv4 目标，不接受域名或 IPv6，不进行目标 DNS 解析。明确拒绝内网、回环、链路本地、共享地址空间、组播、保留、未指定及其他非公网单播地址，不能只用“不是 RFC1918”代替完整校验。项目组应固定并测试支持发行版上 Python `ipaddress` 行为差异涉及的特殊网段。

服务只执行真实 socket connect 与关闭，不接收 shell 命令、路径、探测次数、任意超时、原始数据或可执行脚本。限制行长度、会话寿命、请求次数和并发，socket、线程名额及计时资源在成功、拒绝、超时和异常退出时都要释放。

允许本机来源意味着本机其他进程也可访问该端口；这不是对同机恶意 root 或恶意本地进程的隔离措施。节点仍应由管理员按原产品方式管理用户与访问权限。

原部署流程只传单个安装脚本。将 v2 服务 Python 源码以固定 heredoc 内嵌在此文件中，使用现有 Python 3 依赖，不追加外部代码下载、不新增第二个安装命令、不新增客户菜单。

建议纳入现有事务的资源：

| 资源 | 位置 |
| --- | --- |

把 companion 的文件快照、原运行状态、enabled/disabled、runtime enable、masked/runtime masked 状态纳入现有事务。必要启停、daemon-reload、启动健康检查以及出错恢复都必须覆盖 companion。恢复过程中保留原有 MSBOOST 凭据和原防火墙所有权逻辑，不因新增测速而改变它们。

正常生命周期需明确：新部署成功时启用主服务及 companion，并验证两者运行；主项目执行节点停止、重启和卸载时同步处理 companion。可通过 unit 依赖或现有服务管理入口实现，但不得只在安装末尾临时启动后遗留不受管理的进程。Windows BAT 的启动/停止操作只管理本地核心，不通过 SSH 操作节点服务。

本轮产品范围是**新部署自动支持**；不新增“旧节点保配置升级”界面或客户二次安装流程。上述事务要求仍适用于部署重试和失败恢复，不能以新部署为由省略未知资源保护。

### 原部署自测

在原有本地 SOCKS5/Mieru 自测会话中新增：真实本地 SOCKS5 → Mieru → 节点 `127.0.0.1:20424` 的 hello，并验证版本、nonce、node_id 和精确字段。只在服务端直接用 Python 连回环成功，不能代替这项代理链路自测。

hello 证明协议可达，不能证明远端连接确认时机。目标实际 connect 成功、拒绝、超时和透明转发路径的时序仍需独立验收。部署自测应关闭自己的 socket 和临时进程，不残留监听。

### `internal/executor/cleanup.go`

主项目现有清理机制使用严格路径、目录内容和 unit 身份白名单。需同步加入 `/etc/msboost/relay_tcp_probe.py`、`/etc/msboost/tcp-probe.json` 和 companion unit，更新清理预览、摘要、确认后的实际删除及单元测试。

只接受本项目精确 unit 模板及预期所有权，拒绝 symlink、未知 unit 指令、drop-in、额外命令、额外权限或不明文件。清理时先停用 companion 再移除其程序，确保不会误操作第三方服务。主服务和 companion 生命周期都必须在 preview 中可见，不能扩大通配符删除范围。
